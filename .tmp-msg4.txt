fix: decide the browser step before running it, not by sniffing stderr

Review of the tooling built in the last two passes. Three defects, all in code I
wrote, all in the failure paths that only show up on someone else's machine.

verify_release decided whether to run the browser checks by running them and looking
for "Cannot find package" in the output. `bun x` never emits that: it resolves and
downloads the package. So the skip could never fire, and a run intended only to check
things would silently install a dependency, mutate node_modules and rewrite the lock
file - which is exactly how bun.lock got into a format CI could not read earlier this
session. The decision is now a filesystem check made before the step is built, so the
run has no side effects and the skip is reachable. Verified by moving node_modules
aside: it reports the skip and names the fix. --require-browser turns the skip into a
failure for anyone who wants the check to be mandatory.

The workflow tool audit was checking the wrong thing. It marked the bare `bunx` binary
as installed whenever a job ran `bun install`, and then looked for bunx tools inside
the install line - which never names one. So it validated nothing while passing.
Scoped per job now: the tools a job launches are recorded, and they are only considered
resolved if that same job installs dependencies. A failure names the tool. Verified by
deleting the install step from the workflow and watching it report
"runs `bunx playwright` with no install step".

The README still described CI as "bun test and a static parse check on every push".
There are six jobs now, including real-browser layout checks, and neither
verify_release nor the Playwright suite was documented anywhere. Rewritten, with the
lockfile caveat that cost a red build today.

25 workflow tests, 180 unit tests, 35 browser checks green on Bun 1.2.14 and 1.4.0.
